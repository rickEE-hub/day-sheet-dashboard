# Day Sheet — project memory

Public, no-login warehouse-ops dashboard for Event Equipment Group (Sydney/NSW).

- Repo: `rickEE-hub/day-sheet-dashboard`.
- Data source: Rentman (via the `Rentman` MCP server) — there is no live sync (see "Live schedule refresh — tried and reverted" below for why). As of 2026-09-08, refreshes happen automatically via two Routines (Claude Code scheduled triggers), not on-demand requests to Claude — see "Automated refresh schedule (Routines)" below.
- **Hosting is migrating from Netlify to Cloudflare Workers** (started 2026-09-02) because Netlify meters production deploys against a monthly credit allowance that a 5x/day refresh cadence burns through fast; Cloudflare Workers Builds' free tier (500 builds/month) comfortably covers that volume at $0. See "Cloudflare deploy" below for current status — until cutover is confirmed working, the Netlify site stays up as a fallback (see "Legacy: Netlify" at the bottom).

## Multi-state expansion (NSW + VIC + QLD, added 2026-09-22)

Originally the whole sheet was NSW-only. At Rick's request the dashboard now tracks all three states the company operates warehouses/crew from — NSW, VIC, QLD — everywhere, not just in Rentman queries.

- **Rentman fetch recipe step 3's eligibility filter** now keeps `asset_location_from` in `{"/stocklocations/1" (NSW), "/stocklocations/4" (VIC), "/stocklocations/5" (QLD)}`, not NSW-only — see the recipe below for the full rule including the still-mandatory status filter.
- **Every job object gets a new required `state` field** (`"NSW"`, `"VIC"`, or `"QLD"`) — see "Baked data mechanics" for the exact shape. Unlike `address`, this is not optional: every eligible subproject resolves to exactly one of the three states via its `asset_location_from`.
- **Color coding (fixed, not provisional like the category colors): NSW blue, VIC green, QLD red.** CSS custom properties `--state-nsw`/`--state-nsw-soft`, `--state-vic`/`--state-vic-soft`, `--state-qld`/`--state-qld-soft` were added to all three color blocks (light, `prefers-color-scheme` dark, explicit dark) of every HTML file that renders jobs (`index.html`, `view.html`, the three `view-<state>.html` files, `wallboard.html`, `history.html`). Light values: NSW `#2454E8`, VIC `#0E9F6E`, QLD `#DC2626`. These deliberately reuse the same hex values already assigned to `--cat-install`/`--cat-delivery`/`--cat-operator` respectively (they read fine at a glance since state badges and category chips never sit in the same visual slot), not a coincidence to "fix" — don't consolidate the tokens, they're conceptually different things (state vs. category) that happen to share a palette.
- **Where the color shows, per Rick's explicit answer when asked:** (1) on the state-switcher buttons themselves (`.state-tab-nsw`/`.state-tab-vic`/`.state-tab-qld` etc. — solid state color when active, soft-tinted outline when not), and (2) on every job card, via a `border-left:4px solid var(--state-<key>)` inline style plus a small colored `.state-badge` pill (text "NSW"/"VIC"/"QLD") next to the status pill in the job header. The badge/border render on every page regardless of whether a state switcher is present — even on the locked single-state contractor pages, where they're redundant but harmless (keeps `jobCardHtml()` identical everywhere, one function to maintain).
- **The ALL/NSW/VIC/QLD switcher pattern** (`applyStateFilter()` / `updateStateTabs()` / `loadStateFromStorage()` in `index.html` and `view.html`; the equivalent `applyWallStateFilter()` / `setWallState()` in `wallboard.html`, since that file's day data is keyed by date string rather than day-offset and computed once at load) filters `schedule.days` client-side against `job.state`; `ALL` shows everything unfiltered. `index.html` and `view.html` persist the choice to `localStorage['ds-state']`; `wallboard.html` persists to `localStorage['wallboard-state']`. Default state on load is `ALL` for all three (a deliberate choice — the whole point of this feature is a national at-a-glance view; NSW-only was the old default and is one click away).
- **The three `view-<state>.html` contractor pages have no switcher UI at all** — `selectedState` is set once to a fixed literal (`'NSW'`/`'VIC'`/`'QLD'`) and every switcher-related function/element (`state-tabs` markup, `els.stateTabs`, `updateStateTabs()`, `loadStateFromStorage()`, the click-wiring block) is stripped out entirely rather than just hidden, so there is no client-side code path that could ever show a contractor another state's jobs. Generated by a one-time script transform off `view.html`'s post-feature source (see git history, commit around 2026-09-22) — if `view.html`'s renderer changes going forward (new fields, new card layout, bug fixes), port the same change by hand into all three `view-<state>.html` files too, the same way `jobCardHtml()`/`renderRow()` etc. are already kept in sync across every page per this project's fully-self-contained-HTML convention.
- **Not mirrored to the root-level Netlify fallback** (`index.html`/`view.html` at repo root) — same reasoning as `wallboard.html`/`history.html`: Netlify is being retired, this is new functionality not a fix, and the root files stay frozen at their last NSW-only bake until Netlify is decommissioned (see "Legacy: Netlify" below).
- **Manual items (the "+ Add item" feature) carry a `state` field too (fixed 2026-09-22).** The initial rollout above only gave Rentman-sourced jobs a `state` — manual items had none, so they silently showed on every state filter regardless of which state they were actually for. Fixed by: (1) `sanitizeItem()` in `worker/src/index.js` now validates `input.state` against a `STATES = ["NSW","VIC","QLD"]` allowlist, defaulting to `"NSW"` same as `category` defaults to `"other"`; (2) the add/edit item form in `index.html` gained a "Stock location" `<select>` (NSW/VIC/QLD) next to the Category field, defaulting to whichever state is currently selected in the page's own ALL/NSW/VIC/QLD switcher (falling back to NSW when the switcher is on ALL, since an item can't itself be "all states"); (3) `itemsForDay` filtering in `index.html`/`view.html` now checks `(item.state || 'NSW') === selectedState` the same way job filtering already checked `job.state`, so `ALL` shows every item and a single state shows only that state's; (4) `manualCardHtml()` in every page that renders manual items (`index.html`, `view.html`, and by extension the three `view-<state>.html` files derived from it) got the same `border-left` + `.state-badge` treatment as `jobCardHtml()`, so manual items are colour-coded identically to Rentman jobs. `wallboard.html` was never in scope here — it doesn't render manual items at all (only `schedule.days` jobs), so nothing needed to change there. **Whenever `view.html`'s manual-item rendering changes again, re-run the `view.html` → `view-<state>.html` transform (see the bullet above) rather than hand-editing the three locked files** — that's what was done for this fix.

## Cloudflare deploy (Workers Builds / Git integration)

2. Connect the `rickEE-hub/day-sheet-dashboard` GitHub repo.

4. Production branch: `main`. Deploy command defaults to `npx wrangler deploy` — leave as-is.
5. Save and deploy. Every subsequent push to `main` rebuilds and redeploys automatically (free, well within the 500 builds/month tier at this project's volume).
6. The site is served at the assigned `*.workers.dev` subdomain (Rick chose the free subdomain over a custom domain on 2026-09-02) — record the final URL here once known.

## Live schedule refresh — tried and reverted (2026-09-08/09)

A Cron-Trigger-driven design was fully built, deployed, and then reverted within about a day. Recorded here so nobody re-derives this from scratch:

**What was built:** `worker/wrangler.toml` got a `[triggers]` cron section; `worker/src/index.js` gained a `scheduled(event, env, ctx)` handler calling `buildSchedule(env)`, a JS port of the "Rentman fetch recipe" below that hit `https://api.rentman.net` directly with `fetch()` and wrote the 14-day result to a `DAY_SHEET_KV` key, plus `GET`/`POST /api/schedule` endpoints and a "Refresh now" button on `index.html`. Timezone math (`sydneyTodayKey`/`sydneyMidnightUtcIso`/`sydneyCurrentHour`, all `Intl`-based, no hardcoded UTC+10) worked correctly across DST. All of this deployed cleanly and the `/api/schedule` routing worked.

**Why it was reverted:** every call to `https://api.rentman.net/projectfunctions` with a self-serve API token (Rentman → Settings → Configuration → Account → Integrations → API → Show token) came back `403`: `{"Message":"User is not authorized to access this resource with an explicit deny in an identity-based policy"}`. This is Rentman's own backend (AWS API-Gateway-style) rejecting the request — not a bad token format (`Authorization: Bearer <token>` was cross-checked against several independent real-world Rentman integrations on GitHub, all using the identical header). Reproduced twice: once with a token generated under Rick's own "Operations"-role account, once with a fresh token an admin generated specifically to rule out a role problem — **both got the identical error**, which means it isn't about which Rentman user made the token. Meanwhile the `Rentman` MCP server used interactively in Claude sessions (a separate, officially-integrated channel — not the self-serve token flow) reads `/projectfunctions` successfully every time. Most likely explanation: Rentman scopes self-serve "openapi"-type tokens to a subset of resources that excludes Crew Scheduling data, separate from account/role permissions — but this needs Rentman support to confirm, since the exact wording is their infrastructure's, not something guessable from outside.

**Current status:** reverted. Rick is asking Rentman support directly whether self-serve tokens can be granted this access. If they confirm yes and say what's needed, the cron design can be resurrected from this section's git history (commits from 2026-09-08 on the `claude/new-session-gonbfm` branch, PRs #1 and #2) rather than rebuilt from scratch. Until then, schedule refreshes are back to the manual "pull via Rentman MCP, bake into 4 HTML files, push" workflow below.

## Automated refresh schedule (Routines) — added 2026-09-08

Rick wants refreshes to happen on their own, weekdays only, at 7am and 5pm Sydney time — no need to ask a Claude session each time. Two Claude Code Routines (scheduled triggers) do this:

- **"Day Sheet refresh — weekday 7am Sydney"** (`trig_01FTx3VWrcmbajecAYaxddsF`) — cron `0 21 * * 0-4` (UTC).
- **"Day Sheet refresh — weekday 5pm Sydney"** (`trig_01GcqZa8GKBh6SUh114VUdcT`) — cron `0 7 * * 1-5` (UTC).

Both fire into *this specific persistent session* (`session_01UxCH8vvkTYLSRyeEscZ7gM`), not a fresh session per firing. This was a deliberate workaround, not the first choice: fresh-session-per-fire Routines need a `connectors` grant to get Rentman MCP access in the new session, and this org's plan doesn't support that parameter at all (`create_trigger` rejects it outright) — a fresh-session Routine created without it fires into a session with no MCP connector tools, which can't do anything useful here. Binding to this already-running session sidesteps that entirely, since it already holds live Rentman + GitHub access. **The real implication: these Routines only work as long as this session stays alive.** If it's ever archived/expires, recreate them (same two cron expressions, prompts describing the refresh task — see git history or ask a Claude session to reconstruct from this section) bound to whatever session replaces it, or try `connectors: ["Rentman"]` on a fresh-session Routine again in case the org's plan changes.

**Cron expressions are UTC-only — no timezone support** — the two above assume AEST (Sydney standard time, UTC+10), correct now (September). Once DST starts (~2026-10-04, first Sunday of October) Sydney moves to AEDT (UTC+11), and these will fire an hour early Sydney-time until adjusted: change the 7am trigger to `0 20 * * 0-4` and the 5pm trigger to `0 6 * * 1-5`. Revert both when DST ends (~2026-04, first Sunday of April) back to `0 21 * * 0-4` / `0 7 * * 1-5`. Use `update_trigger` with the trigger IDs above — no need to delete/recreate.

## Rentman fetch recipe (authoritative — follow exactly, every refresh)

**Never shortcut a refresh by diffing `projectfunctions` against the last pull and only re-fetching crew/vehicles for rows that changed.** A pure crew reassignment (swap Mick Rocco for PJ Hamilton-Shailer on an otherwise-unchanged function) does not touch the function's own timestamp, so a functions-only diff misses it silently — this happened for real on 2026-09-08 (NATIS26 AV Packdown, function 5505, and separately The Big Design Market's Exhibition Check Off, function 5120) and produced a live site showing the wrong crew member with no error anywhere. Every refresh — manual or via the automated Routines — must fetch crew and vehicles fresh for every surviving function row, every time, full stop.

**Never hand-attribute a function to a subproject from memory — always read the function row's own `subproject` field, every single time, when building the JSON.** On 2026-09-22 function 5241 (AV Packdown, 2026-10-02) was mis-typed into subproject 1504 (Gamuda/PHIVE, Parramatta) in the baked schedule, when its actual `subproject` was 1507 (FSRACA 2026 - Steris, Gold Coast QLD — at the time this was caught, the sheet was still NSW-only, so 1507 should have been excluded entirely on location grounds too; QLD became eligible later that same day when the multi-state expansion below landed, and 1507/fn5241 correctly re-entered the sheet under Steris, not Gamuda). This put a fake "Gamuda packdown" on the site for a full refresh cycle before Rick caught it. The error propagated silently across two more refreshes because subsequent cycles only re-checked the (already-wrong) set of included subprojects/functions rather than re-deriving inclusion from each function's own `subproject` link. When assembling the day-by-day JSON: group functions by their literal `subproject` field from the step-1 query result, never by which project/subproject you "remember" a function belonging to — and after building the schedule, spot check that every row's function id traces back through the raw query data to the subproject it's nested under before pushing.

1. Query `projectfunctions` → action `list`, filter `{"planperiod_start[gte]":"<ISO>","planperiod_start[lt]":"<ISO>","type[neq]":"shift"}`, fields `"id,name,type,planperiod_start,planperiod_end,subproject,project,amount,in_planning"`, limit 500.
2. **Mandatory filter: `in_planning === true`.** This field is the API equivalent of the "Show in planner" toggle on each function in Rentman's "Crew and transport" UI tab, and it is what actually determines whether a function shows up in the "Crew scheduling" tab. **Discard any row where `in_planning` is not `true`**, regardless of its `type` (this is not a type-based rule — e.g. a `transport_function` can have `in_planning:true` and belongs on the sheet; a `crew_function` can have `in_planning:false` and must be dropped). Confirmed by the user (2026-09-02) against Rentman UI screenshots: "You should not get the data from the 'crew and transport' tab, but yes on 'crew scheduling' only. I have the option to show in planner or not, and you should follow that!" — this is a permanent rule, not a one-off fix.
3. Resolve each unique `subproject` via `subprojects` → `get`, `expand="location,status"`. **Keep NSW, VIC, and QLD jobs (expanded from NSW-only on 2026-09-22, see "Multi-state expansion" above):** `asset_location_from` in `{"/stocklocations/1" (NSW), "/stocklocations/4" (VIC), "/stocklocations/5" (QLD)}`, and `status.id` in `{1,3,4,5,6}` (1=pending, 3=confirmed, 4=prepped, 5=onlocation, 6=returned; excludes 2=canceled, 7=inquiry, 8=concept). **Record which of the three the subproject resolved to as the job's `state` field** (`"NSW"`/`"VIC"`/`"QLD"` — this is a new, non-optional field on every job, distinct from the location's own `visit_state`/`mailing_state` text used for the address). While you're in there, also capture the job's `address` (added 2026-09-21) from the same `location` object: `visit_number + ' ' + visit_street` (trim, drop empty parts) + `', '` + `visit_city + ' ' + state + ' ' + visit_postalcode` (again trim/drop-empty), normalizing the address's `state` text to the abbreviated form (`"NSW"`, `"VIC"`, `"QLD"`) when Rentman returns the spelled-out full name (e.g. `"New South Wales"`, `"Victoria"` — it's inconsistent about which form a given location record uses). Fall back to the `mailing_*` fields if `visit_*` is empty. Like venue/status/state, only re-fetch this when a subproject is newly resolved — carry it forward on later cycles rather than re-fetching every time.
   - **Timezone note (confirmed 2026-09-11):** Rentman's API interprets a bare/naive timestamp string (no UTC offset, e.g. `"2026-09-11T00:00:00"`) in the `planperiod_start[gte]`/`[lt]` filter as **Sydney local time**, not UTC. Pass Sydney-local wall-clock times directly — do NOT convert to UTC first (e.g. don't subtract 10/11 hours for "Sydney midnight in UTC"). Doing that shifts the window ~10-11 hours early and leaks in a stray function from the day before (caught on 2026-09-11: function 5381 from 2026-09-10 leaked into a window meant to start 2026-09-11, using the old subtract-offset approach; passing `"2026-09-11T00:00:00"` directly fixed it).
4. Fetch crew via `projectcrew` — filter `{"function":"/projectfunctions/<id>"}`, expand `crewmember`, **`fields` param is required** (e.g. `"id,function,crewmember"`) or the call fails.
5. Fetch vehicles via `projectvehicles` — same pattern, expand `vehicle`, fields `"id,function,vehicle"`. Vehicle label = `vehicle.displayname + ' · ' + vehicle.licenseplate`.
6. `classify(name)` keyword categorization (keep in sync with the JS in both HTML files): priority order — test → driver → operator/forklift/scissor lift/boom lift/crane/ehs → delivery/deliver → collection/pickup/pick up/pick-up/return → packdown/pack down/pack-down/bump out/bump-out/bumpout/strike/de-rig/derig/teardown/dismantle → setup/set up/set-up/install/bump in/bump-in/bumpin/build up/build-up/rig → warehouse/restock/stocktake/stock take/prep/sorting → other. `warehouse` sits *after* install/packdown deliberately so "Warehouse Pack Down" still reads as a packdown; `operator` sits high so "Forklift Operator" isn't swallowed by another rule.
7. Before discarding the old window: archive any day that's rolling off into `worker/public/archive/`. See "History archive" below — this is a mandatory step now, not optional.

## Resolving a Rentman "project number" the user gives you

Rick refers to jobs by Rentman's user-facing **project number**, which is the `number` field on the `projects` resource — **not** the internal `id`. To resolve: `mcp__Rentman__projects` → action `list` → filter `{"number": "<N>"}` (must be a **string**, not numeric — the API rejects a numeric filter value). Returns the project's internal `id`; use that to find its subproject(s) and functions.

## Baked data mechanics

- Schedule JSON lives at `<script id="app-state" type="application/json">{"items":[],"notes":{},"schedule":{"updatedAt":"...","days":{"YYYY-MM-DD":[...]}}}</script>` in **six files**: `worker/public/index.html`, `view.html`, `view-nsw.html`, `view-vic.html`, `view-qld.html`, and `wallboard.html` (expanded from three to six on 2026-09-22 when the per-state contractor pages were added — see "Multi-state expansion" above). `history.html` is not part of this group — it reads `worker/public/archive/*.json` instead, never the live `app-state` blob. The root-level Netlify fallback `index.html`/`view.html` are also not part of this group any more — they stay frozen at their last NSW-only bake (see "Legacy: Netlify" below). Keep the `schedule` portion byte-identical across all six live files on every refresh — every page reads the exact same 14-day, all-three-states baked window, it's six different renderers/filters over identical data, not six separate fetches.
- Each day bucket is an array of jobs; each job has `id`, `title`, `status`, `venue`, `state` (`"NSW"`/`"VIC"`/`"QLD"`, added 2026-09-22, non-optional — see the fetch recipe's step 3), an optional `address` (added 2026-09-21 — see the fetch recipe's step 3 for sourcing/format; renders as a third, smaller/lighter line under the venue in the job card, right below the existing bold-title/venue layout — omit the field entirely rather than an empty string when a location has no usable address, every renderer treats it as optional) and a `rows` array of projectfunction rows (id, name, category, start, end, needed, crew, vehicles).
- After any data edit: bump `schedule.updatedAt` (ISO 8601 UTC), validate the JSON parses, `node --check` the inline `<script>` logic block, and ideally screenshot with Playwright (`/opt/pw-browsers/chromium`) to visually confirm before pushing.
- A function outside the currently-baked date window (e.g. an "AV Packdown" a couple of days after setup) is real but simply won't render until the window is refreshed to include it — note this to the user rather than silently adding it out-of-window.
- **A function created or edited in Rentman *after* a given day's refresh already ran won't appear until the next refresh** (the next scheduled 7am/5pm Routine, or a manual one) — this is expected staleness, not a bug in the filter/classify logic. If Rick reports something Rentman shows that the live site doesn't, check the function's `created`/`modified` timestamp against the last bake's `updatedAt` before assuming anything else is wrong (see the 2026-09-08 LED Poster Board Hire / function 5548 case in "Active manual overrides" above — Rentman was correct, the bake was just a few hours stale).
- `items`/`notes` in this same JSON block are legacy/unused now that those are fetched live from `/api/items` and `/api/notes` — leave them as empty defaults (`[]`/`{}`), they're overwritten client-side on load.

## History archive (`worker/public/archive/`, added 2026-09-20)

Rick wanted a way to see past jobs instead of them just vanishing once they roll off the 14-day window. Solution: a static, no-server archive, free on Cloudflare's tier.

- `worker/public/history.html` — read-only page at `/history` (Worker rewrite, same pattern as `/wallboard`). Month `<select>` (populated from `archive/index.json`) + day chips (populated from that month's file) + the same job-card renderer as the other pages. Pure static fetches, no KV, no Worker logic beyond the path rewrite — this was deliberately chosen over a KV/API-backed design (Option B considered and rejected) specifically to stay free and require no new server code, per Rick's ask.
- `worker/public/archive/index.json` — `{"months":["YYYY-MM", ...]}`, sorted ascending. The only thing that tells `history.html` which month files exist (there's no directory listing over static assets).
- `worker/public/archive/YYYY-MM.json` — one file per month, `{"days":{"YYYY-MM-DD":[...jobs...]}}`, same job/row shape as the live `schedule.days` (job `id` always `"subN"`, row `id` always `"fnN"` — normalize on write if ever pulling from an older bake that used bare numeric ids, see the 2026-09-20 backfill for why).
- **Every future refresh (scheduled or manual) must archive outgoing days, not just overwrite them:** before replacing `schedule.days` with the new window, diff the *old* baked `schedule.days` (whatever was live going into this refresh) against the *new* window's start date — any day strictly before the new start date is rolling off and must be merged into `archive/<that day's month>.json` (create the file/add the month to `index.json` if it doesn't exist yet) before it's discarded. Skip days that already have zero jobs (nothing worth archiving). This is a small extra step in the existing bake script, not a new workflow — do it in the same Python pass that builds the new schedule JSON.
- Backfilled once on 2026-09-20 by walking every git commit that touched `worker/public/index.html` (`git log --reverse -- worker/public/index.html`), extracting each commit's `schedule.days`, and keeping the last-seen state of every date not in the then-current live window — recovered 16 days back to 2026-09-02. No need to repeat this; going forward the per-refresh step above keeps it current.
- Not mirrored to the root-level Netlify fallback — Worker-only, same reasoning as `wallboard.html` (Netlify is being retired; this is new functionality, not a fix).
- Both `index.html` and `view.html` link to `/history` from their masthead button row (`.btn` was given `display:inline-block; text-decoration:none;` so an `<a class="btn">` matches the `<button class="btn">` styling exactly). `wallboard.html` does not — it's an unattended passive TV display, not something anyone clicks through.

## Day window — 14 days (changed 2026-09-07)

The sheet started as a 3-day view, went to 5, and is now **14 days** at Rick's request. `DAY_OFFSETS` in the inline `<script id="app-script">` of all 4 HTML files is `[0..13]`. Day tabs are 14 static `.day-tab` buttons in the markup, laid out as a CSS grid — `repeat(7,1fr)` (7 across, 2 rows) on desktop, `repeat(4,1fr)` (4 across, 4 rows) at `max-width:640px`. **Every Rentman refresh must now bake 14 days of `schedule.days` keys** (today + 13), not 5, or the back half of the sheet renders as empty days.

**Day-tab date bug — DST duplicate day (fixed 2026-09-21):** the client-side day-tab labeling (`index.html`/`view.html`, both `worker/public/` and the root Netlify fallback — `wallboard.html`/`history.html` were never affected, see below) used to compute each tab's real Sydney-midnight `Date` instant via a guess-then-correct timezone-offset lookup (`sydneyDayRange`/`sydneyOffsetMs`). That lookup was self-referential exactly at the AEST/AEDT changeover instant (2am Sydney time on the DST-start Sunday) and silently resolved two different offsets to the same calendar date — Rick spotted it as two "SATURDAY 3" tabs with no "SUNDAY 4" crossing into 2026-10-04's DST start. Fixed by replacing it with `sydneyDateForOffset`, which does pure calendar-date arithmetic (today's Sydney `{y,m,d}` + offset days, anchored at UTC noon) instead of computing a real clock instant — the UTC-noon anchor reads as the same calendar date in every timezone on Earth, so DST never enters into it. This is the same pattern `wallboard.html`'s and `history.html`'s `dateFromKey` already used (which is why they were never affected) — **do not reintroduce real-timezone-instant math for what is fundamentally just calendar-date labeling**, anchor at UTC noon instead. `sydneyDayRange`/`sydneyOffsetMs` are gone; `sydneyDateForOffset(offsetDays)` is the one function everything (day tabs, `isoDateForOffset`, the date line, empty-state text) now derives from.
